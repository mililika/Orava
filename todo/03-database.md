# 03 · Database

**Goal:** the Postgres schema (`users`, `transactions`, `sessions`), managed with
migrations, plus seed scripts so a fresh database has a working demo user in one command.

**Depends on:** 01, 02.

## Decisions

- **Only the server connects to Postgres.** The web app never gets a connection string, a
  database key or a database client library. Tables have no public API of their own; every read
  and write goes through a NestJS endpoint that checks the session.
- **Drizzle ORM** with schema in `apps/server/src/db/schema.ts`, SQL migrations generated by
  drizzle-kit into `apps/server/drizzle/` and **committed**. Migrations run with a script
  (`npm run db:migrate`), never automatically on server start (Cloud Run may start several
  instances at once).
- Postgres driver: `postgres` (postgres.js) or `pg`, whichever the current Drizzle docs recommend.
- **Money:** `numeric(12,2)` in the DB, converted to `number` (euros) at the repository layer,
  because the engine in `@orava/core` works in euros as floats.
- **Balance** is never stored per row. Each user has an `opening_balance_eur` (the balance before
  their first transaction). Current balance = opening + sum of non-deleted transaction amounts.
  This keeps deletes and inserts consistent.
- **Naming:** plural, snake_case table names (`users`, `transactions`, `sessions`) and snake_case
  columns; Drizzle maps them to camelCase in TypeScript.
- **IDs:** `uuid` for users (generated with `gen_random_uuid()`), `bigint identity` for transactions.
- Usernames are stored lowercased and trimmed; uniqueness is on that value.

## Schema

```
users
  id                  uuid pk default gen_random_uuid()
  username            text not null unique        -- lowercased
  password_hash       text                        -- null for guest users
  is_guest            boolean not null default false
  opening_balance_eur numeric(14,2) not null default 0
  ai_hourly_limit     integer                     -- null = server default (section 06)
  created_at          timestamptz not null default now()
  expires_at          timestamptz                 -- guests only; cleaned up after this

sessions
  id                  text pk                     -- sha256(token), hex; the raw token is never stored
  user_id             uuid not null references users on delete cascade
  created_at          timestamptz not null default now()
  expires_at          timestamptz not null
  last_seen_at        timestamptz not null default now()
  index (user_id)

transactions
  id                  bigint generated always as identity pk
  user_id             uuid not null references users on delete cascade
  date                date not null
  category            text not null               -- a category name from @orava/core
  type                text not null               -- e.g. purchase, salary; set by the server with typeFor(category)
  merchant            text not null
  amount_eur          numeric(12,2) not null      -- negative = money out
  source              text not null check (source in ('seed', 'user'))
  created_at          timestamptz not null default now()
  deleted_at          timestamptz                 -- soft delete
  index (user_id, date desc, id desc)
```

That's the whole schema: two data tables and `sessions`, which login needs (section 04). No
benchmark, analysis or AI tables; the AI cache and usage limits live in server memory (section 06).

## Tasks

- [ ] Add Drizzle and drizzle-kit to `apps/server`, `drizzle.config.ts`, the schema above, and the
      first generated migration. Scripts: `db:generate`, `db:migrate`, `db:studio` (optional).
- [ ] `DbModule` (global): a provider that creates one connection pool from `DATABASE_URL` and the
      Drizzle instance, injected with a token (e.g. `@Inject(DB)`). Close the pool in
      `onApplicationShutdown`. Add the `select 1` check to `GET /api/health`.
- [ ] Injectable repositories (`UsersRepository`, `TransactionsRepository`) that hide Drizzle from
      controllers and services, for example `findByUsername`, `list(userId)` returning
      `@orava/core`'s `Transaction[]` (newest first, without deleted rows) and `balanceOf(userId)`.
      Section 05 adds the write side. Repositories return domain types, never Drizzle row types,
      and controllers map them to `@orava/contracts` DTOs.
- [ ] Seed and CLI scripts (below) reuse the same Drizzle schema and repositories. Run them as
      plain scripts or through a Nest standalone application context
      (`NestFactory.createApplicationContext`), whichever is simpler.
- [ ] **Seed: demo user** (`npm run db:seed`, idempotent). Creates user `demo` with the password from
      `SEED_DEMO_PASSWORD` (refuse to run if it's missing in production), and the synthetic data from
      `@orava/core`'s demo generator. Opening balance: the generator's `OPENING_BALANCE`. Re-running
      replaces the demo user's `seed` transactions but keeps nothing else.
- [ ] **Admin CLI** `npm run user:create -- <username>`: prompts for a password (hidden input),
      hashes it with the same function auth uses (section 04; leave a TODO until then), and
      optionally copies the demo data with `--with-demo-data`.
- [ ] Root scripts: `db:migrate`, `db:seed` forward to the server workspace.
- [ ] Document the "fresh database" flow in the root README:
      `npm run db:up && npm run db:migrate && npm run db:seed`.

## Acceptance criteria

- A clean `docker compose down -v && docker compose up -d db`, then migrate and seed, produces a
  `demo` user whose `listTransactions` + `balanceOf` give **the same `HealthReport`** as the old
  client-side `demoAccount()` (compare `buildHealth(...)` output for both in a throwaway script; don't commit it).
- `npm run db:seed` run twice doesn't duplicate anything.
- `drizzle-kit generate` shows no pending changes after the first migration is committed.
- `\dt` in psql lists exactly `users`, `transactions`, `sessions` (plus Drizzle's migrations
  bookkeeping table).

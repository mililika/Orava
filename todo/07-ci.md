# 07 · CI

**Goal:** a GitHub Actions pipeline that runs formatting, lint, typecheck and build on every PR,
plus guards that keep the old key leak and any direct database access from coming back.

**Depends on:** 01–06.

**No automated tests.** Don't add a test runner, test files or a `test` script. Correctness is
checked by the type system (shared contracts make server/client mismatches a compile error), zod
validation at runtime, and running the app by hand against each section's acceptance criteria.
See the rule in README.

## Tasks

### CI (`.github/workflows/ci.yml`)

- [ ] On pull requests and pushes to `main`: checkout, set up Node (LTS, with npm cache),
      `npm ci`, `npm run format:check`, `npm run lint`, `npm run typecheck`, `npm run build`.
- [ ] `npm run typecheck` covers every workspace, so changing a schema in `@orava/contracts`
      without updating the server or the web app fails CI.
- [ ] Bundle check: run `npx expo export --platform web` and fail if the output contains
      `generativelanguage`, `x-goog-api-key`, `postgres://`, `postgresql://` or `DATABASE_URL`.
- [ ] Dependency check: fail if `apps/web` depends on a database or AI client (`pg`, `postgres`,
      `drizzle-orm`, `@supabase/*`, `@google/genai`, …). A short script over
      `apps/web/package.json` is enough.
- [ ] Build the server Docker image (no push), so a broken Dockerfile fails the PR.
- [ ] Turn on branch protection for `main` in GitHub (requires the CI checks). The owner does
      this in the GitHub settings; leave a note in the PR.

## Acceptance criteria

- A PR shows the CI checks, all green.
- Adding `pg` to `apps/web/package.json` makes CI fail.
- Introducing a type error in a contract's consumer makes CI fail.

# 06 · AI on the server

**Goal:** move every Gemini call to the server. The browser sends only a month and the chat
messages; the server loads the user's data, builds the prompt, calls Gemini, caches overviews and
enforces usage limits. After this section, there's no AI key or system prompt anywhere in the web
bundle.

**Depends on:** 01, 03, 04, 05.

## Decisions

- **The server builds the prompt from its own data.** The client never sends a system prompt,
  transactions or a report. That's what keeps this from being an open Gemini proxy that anyone could
  use for anything.
- **Gemini access:** port the existing REST code from `apps/web/src/lib/gemini.ts` (it already
  handles streaming, JSON schemas and the thinking-level retry) to Node's built-in `fetch`.
  Switching to the official `@google/genai` SDK is fine if it makes the code simpler; check its
  current docs. Locally, use a Gemini API key from Google AI Studio (`GEMINI_API_KEY`). Vertex AI
  with the Cloud Run service account is an option for later (see `09-later.md`).
- **Model and thinking level** stay configurable: `GEMINI_MODEL` (default `gemini-3.8-flash`, as
  now) and `GEMINI_THINKING` (default `low`). Check that the default model still exists before
  relying on it.
- **Streaming to the browser:** Server-Sent Events. Events: `delta` (`{ text }`, the reply so far
  or the new chunk; choose one and document it), `done` (`{ text }`), `error`
  (`{ code, message, retryAt? }`).
- **Limits** (kept **in server memory**, no database tables; each Cloud Run instance counts on its
  own, which is fine with max 2 instances; see `09-later.md` if that ever isn't enough):
  - per user per rolling hour: `users.ai_hourly_limit`, else `AI_HOURLY_LIMIT` (default 30);
  - a global daily cap across all users, `AI_DAILY_LIMIT` (default 2,000): a last line of defence
    for the bill.
  - Over a limit → 429 with `{ code: 'ai_limit', retryAt }`; the existing `LimitModal` shows it.
  - Overview cache hits don't count.
- **Chat history:** the client sends the visible conversation each time (as now), capped at the
  last 20 messages and 2,000 characters per message. Chats aren't stored on the server.

## API (all need a session)

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/api/ai/overview?month=YYYY-MM` | none | `{ overview: { summary, good, bad } }` · 429 · 503 |
| POST | `/api/ai/chat` | `{ month, messages: [{ role: 'user' \| 'model', text }] }` | SSE stream |

## Tasks

### Contracts (first)

- [x] `packages/contracts/src/ai.ts`: `OverviewQuery` (`{ month: Month }`), `OverviewDto`,
      `OverviewResponse`, `ChatMessage`, `ChatRequest` (with the caps above), `AiLimitError`
      (`{ code: 'ai_limit', message, retryAt }`), and the SSE events as a discriminated union
      `ChatEvent` = `delta | done | error`. Both the server (to write events) and the web app (to
      parse them) use `ChatEvent`.

### Server (`AiModule`)

- [x] Move `coach.ts` (persona, `coachContext`, `coachSystem`, `plainText`) from `@orava/core`
      to `apps/server/src/ai/coach.ts`. The prompt is server-only now. Keep the wording as is.
- [x] Move the overview prompt, `SCHEMA` and `parse()` from `apps/web/src/orava/overview.ts` to
      `apps/server/src/ai/overview.ts`. Validate Gemini's JSON reply with `OverviewDto` instead of
      the hand-written `parse()`.
- [x] `GeminiService`: `ask(system, turns, { schema, signal })` and
      `stream(system, turns, onText, { signal })`, ported from the web app's `lib/gemini.ts`.
      Log input and output token counts from the response's usage metadata (pino, per request).
      Inject it through an interface token, so another provider (Vertex AI, see `09-later.md`) can
      replace it without touching the callers.
- [x] `AiLimitsService.take(user, kind)`: in memory, a rolling one-hour list of request times per
      user plus a counter for the global daily cap. Check and record in one synchronous step, so
      two parallel requests can't both take the last slot. Throws an `HttpException` that the
      global filter turns into 429 `AiLimitError`. The per-user limit comes from
      `users.ai_hourly_limit` when set.
- [x] `GET /api/ai/overview`: load transactions and balance, `reportForMonth` from core,
      `signatureOf` for the cache key; return the cached row if the signature matches; else take a
      request slot, ask Gemini, store it in the cache, return it. Share in-flight requests per
      `(user, month, signature)` in memory so the Home card and Money health don't ask twice.
- [x] `POST /api/ai/chat`: validate with `ChatRequest`, take a slot, build the system prompt for
      `month`, stream SSE. NestJS's `@Sse()` decorator only supports GET, so write the stream by
      hand with `@Res()`: set `Content-Type: text/event-stream`, `Cache-Control: no-cache`,
      `X-Accel-Buffering: no`, flush headers, write one `data: <ChatEvent JSON>\n\n` per event, end
      the response after `done` or `error`. When the request closes (`req.on('close')`), abort the
      Gemini request through its `AbortSignal`. Errors that happen before streaming starts (limit,
      validation, no key) are normal JSON error responses; errors after it starts are an `error`
      event.
- [x] Overview cache: in memory, keyed by `(userId, month)` and holding the signature, so a changed
      signature replaces the entry. Cap its size (e.g. an LRU of a few thousand entries) so memory
      stays bounded. It's lost on restart or scale-to-zero, which just means one new Gemini call.
- [x] If `GEMINI_API_KEY` isn't set, the AI routes return 503 `{ code: 'ai_unavailable' }` and the
      server still starts (so the rest of the app works without a key).

### Web app

- [x] `src/orava/overview.ts` → a small hook `useOverview(month)` that calls the API. Drop the
      AsyncStorage cache (the server caches now; a short in-memory cache per session is fine).
- [x] `OravaChat.tsx`: send a `ChatRequest` to `/api/ai/chat` through `lib/api.ts`, read the SSE
      stream with `expo/fetch` (browser fetch on web), parse each event with `ChatEvent` and feed
      the existing typewriter. On `ai_limit`, show the
      existing "hourly limit" text; on any other error, fall back to the offline `answer()` from
      `@orava/core`'s `chat.ts`, as now.
- [x] `LimitModal` is triggered by 429 `ai_limit` responses instead of `rateLimit.ts`.
- [x] Delete `src/lib/gemini.ts`, `src/lib/rateLimit.ts`, `rate-limits.json`, and the
      `EXPO_PUBLIC_GEMINI_*` vars from `.env.example` and the README.

## Acceptance criteria

- `npx expo export --platform web` output contains no Gemini key, no `generativelanguage` URL and
  no persona text (`grep -r "money friend" dist` finds nothing).
- Home card and Money health show Gemini overviews for the current and past months; reopening a
  month doesn't call Gemini again (check the server logs).
- Adding a transaction changes the newest month's signature → a new overview.
- The chat streams word by word in the browser.
- Setting `ai_hourly_limit = 1` for a user: the second request gets 429 and the modal shows the
  wait time.
- Without `GEMINI_API_KEY`, the app works, the overview card shows Orava's built-in sentence, and
  the chat answers offline.
- `curl` to `/api/ai/chat` without a session → 401.

## Notes

<!-- Anything that turned out different from this plan. -->
- **REST, no SDK:** `GeminiService` is the web app's REST code ported to Node's `fetch` (streaming,
  JSON schema, the thinking-level retry), behind the `AI_MODEL` token (`ai/ai-model.ts`). No new
  dependency. Token counts are logged per request ("Gemini usage"), never prompts or replies.
- **Fallback model on Gemini's rate limit:** `GEMINI_MODEL` (default `gemini-3.8-flash`) first;
  if Gemini answers 429 (rate limit) or 503 ("high demand", seen in testing) for it, the same
  request goes to `GEMINI_FALLBACK_MODEL` (default `gemini-3.5-flash-lite`; empty = none). It's
  logged as a warning, and the usage log names the model that answered. Both come before any
  text, so the chat stream isn't affected. Our own
  per-user and daily limits are separate and unchanged.
- **`delta` carries the reply so far**, not just the new chunk, which is what the chat's
  typewriter needs. The server runs `plainText` on every delta and on `done`.
- **429 body:** the standard `ApiErrorBody` with `code: 'ai_limit'` and
  `details: { retryAt, limit }` (`AiLimitError`). `limit` is the user's hourly limit, or null for
  the daily cap, so `LimitModal` can say which. The exception filter now passes `details` through,
  and keeps a 5xx's own code when it was thrown with one (503 `ai_unavailable`).
- **The daily cap resets at midnight UTC.** The hourly limit is a rolling hour, as planned.
- **A month outside the user's data → 404** on both routes. Without a key, both answer 503 before
  touching the database.
- **Aborting Gemini uses `res.on('close')`**, not `req.on('close')`: on current Node, the
  request's 'close' fires as soon as its body has been read. The handler checks
  `!res.writableEnded`, so a normal end doesn't abort.
- **`ChatEvent.error` is only ever `internal`:** limits and "no AI" are checked before the stream
  starts and come back as JSON errors.
- **JSON body limit raised from 64 KB to 256 KB** (`main.ts`): a chat within the caps can exceed
  64 KB in UTF-8.
- **`useOverview(month, txs)`**, not `useOverview(month)`: the hook needs the transactions to
  notice a changed signature and ask again. Its session cache is keyed by month + signature.
- **Orava's built-in sentence** (`report.orava.message`) now shows on Home and Money health
  whenever there's no Gemini overview (no key, limit, error). Before, the card stayed blank.
- **Removed `@react-native-async-storage/async-storage`:** only the overview cache and
  `rateLimit.ts` used it.
- **`LimitModal`** listens to `lib/aiLimit.ts`, which `lib/api.ts` notifies on every 429 `ai_limit`.
- **Verified without a Gemini key (2026-11-24):** both routes 401 without a session; signed in,
  the overview answers 503 `ai_unavailable`, the card shows Orava's own sentence and the chat
  answers offline; `expo export` contains no key, no `generativelanguage`, no persona text.
- **Verified with a key (2026-11-24):** both `gemini-3.8-flash` and `gemini-3.5-flash-lite`
  exist. 3.8 Flash answered 503 "high demand" on every call that afternoon, so everything ran
  through the fallback. A real overview came from Flash Lite (2.8 s, ~10.7k input tokens), and a
  reload was a cache hit (187 ms, no Gemini call). `GeminiService.stream` against Flash Lite
  streamed 7 chunks, the first after ~1 s. With `AI_HOURLY_LIMIT=1` (env override, not the DB
  column) the second request got 429, the modal showed the wait, and the chat said "Ask me again
  in 60 min". **Not seen end to end:** a Gemini reply streaming into the app's chat, and a new
  overview after adding a transaction. Every chat attempt got 503 from both models, so the app
  showed the offline answer as designed.

# 01 · Repo structure and the shared core package

**Goal:** turn the repo into an npm workspaces monorepo and move the pure domain engine into
`packages/core`, so the server (section 02 onwards) and the web app compute the same Money
health report. Also clean up what the hackathon left behind. The app must look and behave exactly
as before when this section is done.

**Depends on:** nothing.

## Target layout

```
/
  package.json            workspaces: ["apps/*", "packages/*"]; root scripts
  apps/
    web/                  the Expo app, moved from mobile/ (git mv, keep history)
    server/               created in section 02
  packages/
    core/                 @orava/core: pure TypeScript, no React / RN / Node APIs
    contracts/            @orava/contracts: zod schemas + inferred types for the API
  todo/                   this plan
```

The hackathon's `db/` and `docs/` folders are gone. The database lives in Supabase and isn't
defined by any file in the repo; its schema is written out in section 03.

### `@orava/core`

Create `packages/core` (TypeScript, `strict`).

**How shared packages are built** (applies to `core` and `contracts`): NestJS compiles to
CommonJS and relies on decorator metadata, so the server can't load another package's `.ts`
sources at runtime (and esbuild-based runners like `tsx` don't emit decorator metadata). So each
shared package is **compiled to JS** with `tsup` into `dist/`, as both ESM and CJS with `.d.ts`
files, and its `package.json` `exports` map `types`, `import` and `require` to those files.
Metro (web) and Nest (server) both consume `dist/`.
- `npm run build` at the root builds the packages first (`npm run build -w packages/core -w
  packages/contracts`), then the apps.
- The root dev scripts run `tsup --watch` for the packages alongside the web app or server, so
  changes in a package show up without a manual rebuild.
- If the current Expo docs show a cleaner way for Metro to read package sources directly (for
  example a custom export condition), that's fine for the web side, but the server always uses
  `dist/`.

## Notes

<!-- Anything that turned out different from this plan. -->

- **Branch:** done directly on `post-hackathon-improvements` (the owner asked for that), not on a
  separate `…/01-repo-and-core` branch.
- **tsup 8, not 9.** tsup 9 needs Node ≥ 24.11; the dev machine has 24.10, so npm picked 8.5.
  tsup 8's `.d.ts` build sets `baseUrl`, which TypeScript 6 deprecates, so both `tsup.config.ts`
  pass `ignoreDeprecations: '6.0'` to the dts build only. Revisit when moving to tsup 9.
- **`exports`** use nested conditions so CJS consumers (the server) get `index.d.cts`:
  `import → { types: index.d.ts, default: index.js }`, `require → { types: index.d.cts, default: index.cjs }`.
- **Packages are built on `npm install`** (root `postinstall` runs `build:packages`), so lint and
  typecheck work right after a fresh clone. Root `typecheck` also rebuilds them first, so the web
  app never typechecks against a stale `dist/`. Root `.gitignore` now ignores `dist/`.
- **Root scripts:** `web` and `start` build the packages, then run `tsup --watch` for both
  packages next to Expo with `concurrently` (root devDependency). In watch mode tsup doesn't wipe
  `dist/` first, so Metro never sees it empty. `build` = packages, then `expo export --platform web`
  (new `build` script in `apps/web`). `lint` and `format` run in every workspace; the packages
  have their own `eslint.config.cjs` (Expo's config + Prettier, like the web app).
- **No `metro.config.js`:** the Expo monorepo guide says SDK 52+ configures Metro for workspaces
  automatically, and it works.
- **Categories:** core has `CATEGORY_LIST` (as const), `Category`, `CATEGORIES` (name, income),
  `isCategory`, `categoryInfo`, the add-screen lists and `typeFor`. The web app's
  `src/data/categories.ts` keeps `CATEGORY_STYLES` (icon, tint, keyed by `Category`) and a
  `categoryInfo()` that merges both, so components didn't change.
- **Moods:** core has `MOOD_LABELS` (name, who); the web app's `MOODS` spreads them and adds colours.
- **`TransactionDto.category` is `z.string()`, not the `Category` enum,** so it matches core's
  `Transaction` exactly (checked in `contracts/src/checks.ts`) and dataset rows with an unlisted
  category still parse (they show as "Other"). The `Category` enum is exported for request
  bodies (section 05).
- **`auth.ts`, `account.ts`, `ai.ts` in contracts are empty** (`export {}`) and not re-exported
  from `index.ts` yet (ESLint's `import/export` rejects `export *` of a module with no exports).
  Each section adds the `export *` line with its first schema. ESLint's `no-redeclare` is off in
  contracts, since each schema and its inferred type share a name.
- **The purity grep** in the acceptance criteria also matches `export` (the `expo` alternative is
  unanchored). The intended check, `grep -rE "from '(react|react-native|expo)" packages/*/src`,
  finds nothing.
- **Demo data removed in this section (owner's call), not in 04–05.** `data/demoAccount.ts` and the
  "Continue with demo data" button are deleted. Until section 04 wires login to the server, the app
  opens to the sign-in screen and can't sign anyone in, so the acceptance criterion about
  "Continue with demo data" no longer applies. The only hardcoded value left is
  `apps/web/rate-limits.json` (placeholder so the app compiles; section 06 deletes it).
- `.claude/launch.json` (not tracked) now runs `npm run web` from the root.
